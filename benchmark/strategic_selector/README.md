# Pixel 7 strategic mission selector: research archive

Research only, 2026-09-23. This is a text-only synthetic test of a **proposed** high-level script selector. No motor, ESP32, LiDAR, camera, YOLO, map, or person identification ran. The current repo describes a mecanum prototype; a phone-mounted RC car with 2D LiDAR is a proposed redesign. Neither Laya nor Von has been integrated into the motor loop. [The current navigation benchmark plan](../../docs/BENCHMARK_PLAN.md) tests the as-coded path and remains a separate task.

## Cycles and authority

The proposed cycle is: conversational LLM (identity TBD; Gemma is a candidate) obtains a bounded objective → timestamped map/room, sensors, vision, mission history and last script result describe state → Laya or Von chooses an eligible script (search, travel, call/listen, relocalize, finish, or ask the LLM to revise the objective) → Python controls local movement and obstacle response with ESP32 interlocks/watchdog → verified completion returns to the human. Travel may require a second model decision for the destination. An example ~20-second script duration is hypothetical. Map alignment, camera–LiDAR association, named-person verification, safe script interruption, model co-residency, and controller gates are unbuilt or unverified. YOLO's `person` class does not establish identity. Model scores or confidence cannot serve as brakes or safety guarantees.

The **as-coded** `main.py:Robot.run_cycle()` takes a photo, runs YOLO, calls `navigate_rules()`, sometimes consults Gemma on triggers, restores Python-selected safety moves, then may send a motor command. `docs/STATUS.md` says the intended LLM-free navigation change in DECISIONS #104 is pending; the trigger code still exists. This archive does not alter that code.

## Exact strategic experiment

Executed v2 source: [robot_selector_benchmark.py](robot_selector_benchmark.py), SHA-256 `3aa9d399d6978710c143a6f1dfe69541b288cea329f27077b2500e322e8c14e2`. Its run logs print `BENCHMARK_VERSION=2`. The Downloads file literally named `robot_selector_benchmark.py` is **v1** (`334941f4476edb4f9a9065089f7b40a96d4215d0f00699a28f4102450b659953`). The requested download SHA `148534c148075e1a0bc1c4bef12f7b36704e845be45f1898c92c0e47e7dab8a8` matches `robot_selector_benchmark-1.py`, a v2 candidate. It differs from the executed v2 only by two explanatory comment lines; the executed bytes are archived here. [The executed v1 source](robot_selector_benchmark_v1.py) is retained for its historical Laya run.

Device was a Pixel 7 in Termux/Debian proot, aarch64, Python 3.13.5, PyTorch 2.14.0+cpu, four intra-op threads, one inter-op thread and affinity cores 4–7. Installed package metadata: `laya` 0.3.2 and `von-sdk` 1.1.1. Laya used `laya.load("convaiinnovations/laya")` and `agent.predict` with `type=choice`, `instructions` and named criteria. Von used `von.decide(state=..., choices=..., instructions=...)`; its runtime reported von-1.1.0 weights from `wfzyx/von:option_marker.pt`. Von printed a Transformers `UNEXPECTED` head-key load report, though the API returned choices. Models used offline caches; no GPU/CUDA.

The script generates 11 scenario families × 3 variants per model. Variants 0–1 are 22 development cases; variant 2 is 11 held-out cases. **Laya and Von see disjoint generated text/room variants**, so percentages are within-model diagnostics, not a controlled head-to-head accuracy comparison. All labels are synthetic and generated by the same script as the states; held-out cases share families with development cases and are not fresh untouched scenarios. Five framings are evaluated on development: `wide_text`, `filtered_text`, `filtered_json`, `two_stage_text`, `two_stage_json`. Filtered frames remove ineligible actions; two-stage frames can make a second destination call. Selection ranks development acceptable count, then preferred count, fewer ineligible choices and median latency. Only the selected frame runs on held-out cases and reversed option order. JSON preserves each state, instruction, offered option, choice, probability, score and decision latency.

`preferred` means exact scripted target. `acceptable` includes any reachable unsearched room for travel, and limited alternate search/call actions. An acceptable destination may still miss the shorter route or a voice clue. `invalid_or_ineligible` checks against filtered options. V1's rubric wrongly accepted only the preferred travel destination and left travel eligible after a confirmed target. V2 changed those two rules; do not compare v1 accuracy to v2 as if only the model changed.

## V2 results

Development, 22 cases per frame; latency is the full decision, including a second call when made:

| Model | Frame | Preferred | Acceptable | Median ms | P95 ms |
|---|---|---:|---:|---:|---:|
| Laya | wide_text | 2 | 4 | 3242.3 | 3536.9 |
| Laya | filtered_text | 10 | 18 | 2503.2 | 3137.3 |
| Laya | filtered_json | 6 | 13 | 3292.3 | 3922.3 |
| Laya | two_stage_text | 8 | 16 | 2579.8 | 5294.6 |
| Laya | two_stage_json | 6 | 13 | 3412.5 | 6695.3 |
| Von | wide_text | 3 | 6 | 3336.4 | 3548.9 |
| Von | filtered_text | 13 | 17 | 2478.8 | 2871.8 |
| Von | filtered_json | 9 | 14 | 3073.3 | 3534.1 |
| Von | two_stage_text | 14 | 18 | 3383.5 | 5025.4 |
| Von | two_stage_json | 10 | 14 | 4742.5 | 6191.0 |

| Held-out, 11 cases | Preferred | Acceptable | Median ms | P95 ms | Order flips | Calls |
|---|---:|---:|---:|---:|---:|---:|
| Laya selected `filtered_text` | 7 | 9 | 3028.8 | 3284.3 | 4/11 | 11 |
| Von selected `two_stage_text` | 4 | 8 | 4797.9 | 5154.9 | 9/11 | 17 |
| Von `filtered_text` post hoc follow-up | 4 | 8 | 2053.8 | 5312.7 | 9/11 | 11 |

The Von follow-up reused held-out cases **after** the initial result was seen. It is a diagnostic, not an independent validation. Its first call took 8179 ms, lifting P95; reversed-order median was 1950.1 ms. The saved follow-up evidence is stdout only: exact wrapper source and JSON rows are missing. Reversing options changed some action types, including confirmed-person `finish` → `ask_gemma` and blocked-route `relocalize` → `call_chiara` for Von. Laya also called again after two unanswered calls and called instead of relocalizing with lost pose. Deterministic guards would need separate validation before any integration.

Laya import/load was about 51 s. Von import/load reported about 12 s, but its first decision separately loaded cached weights, so these numbers have different boundaries. Peak process RSS was about 2848 MiB Laya and 3062 MiB Von, without concurrent full perception or dialogue. These results measure synthetic-script agreement only, not navigation success, target recognition, sensor fusion, safe stopping, or calibrated probabilities.

## Locate evidence and add a future run

[RUN_INDEX.md](RUN_INDEX.md) lists every archived run, gaps and earlier phone experiments. Each run directory has the original raw `results.json` when available, raw `stdout.txt`, and `manifest.json` with original phone path/hash, archived hash, original modification time, runtime, framing, split and follow-up status. [PHONE_HISTORY.tsv](PHONE_HISTORY.tsv) hashes the earlier phone-only speed-test files without copying a separate browser repository or model files. `python archive_run.py verify` checks archived hashes.

For a **new** run on the phone, activate the existing `/termux-home/laya-test/venv`, set `HF_HOME` to the relevant existing offline cache (`/termux-home/laya-test/hf-cache` for Laya or `/termux-home/von-test/hf-cache` for Von), then from this directory run `python archive_run.py run --model laya` or `--model von`. The helper enforces offline flags, uses `taskset -c 4-7`, assigns a UTC time plus random run ID, creates the run directory exclusively, keeps raw stdout and stderr plus JSON, writes SHA-256 hashes, verifies the archive and prints `git check-ignore` and `git status`. It never replaces an existing run. Run one model at a time. A future run should keep its exact package, model, environment and device metadata with the manifest; the helper records command, Python, cache choice through the required environment, source hash and output hashes, while any changed package/model versions must be noted by the operator.

Future evaluation should use genuinely new untouched scenarios, independently score **action type** and **room destination**, permute option order and room names, report ineligible choices, and record per-call plus full-decision latency and whether a second decision was needed. A cross-model accuracy claim requires the same cases and rubric. No model inference was rerun to create this archive.
